# 输入清洗

在提取事实之前，先把不同来源整理成同一种内部结构。清洗只做归类、去重和字段补位，不在这里改写工作成果。

## 推荐的手工粘贴格式

```text
汇报周期：2026-10-27 至 2026-11-02

===== 2026-10-27 | 日报 | 项目：项目A =====
今日完成：……
明日计划：……
风险或需协调：……
```

这只是推荐格式，不是准入门槛。用户直接粘贴钉钉复制内容时，先识别日期、模板、项目字段和正文；不要要求用户重新排版后才能继续。

## 从文本中识别什么

- 日期或明确时间表达。
- 提交人；没有时可以按用户本人处理，但不要写入成品。
- 日志模板名称。
- 项目、系统、业务线或任务对象。
- 今日完成、明日计划、问题、风险、需协调事项等字段。
- 数量、单位、比例、轮次、日期等可核验信息。

一条日报可能包含多个独立事項。不要因为它们在同一个表单字段里就强行合并。

## 钉钉 JSON 映射

`fetch_my_logs.py` 导出的 `data_list` 通常含以下字段：

- `create_time`：日志创建时间，毫秒时间戳，按 Asia/Shanghai 转换。
- `modified_time`：修改时间，毫秒时间戳。
- `template_name`：模板名称。
- `creator_id` / `creator_name`：提交人信息。
- `report_id`：日志唯一标识。
- `contents`：字段数组，每项通常包含 `key`、`value`、`type`、`sort`。

处理规则：

1. 同一个 `report_id` 只保留一条；有多版本时保留 `modified_time` 最新且内容最完整的版本。
2. 不同日期、不同模板或不同提交人的日志不要因为正文相似而直接合并。
3. `contents` 的 `key` 是表单字段名，`value` 是原始内容；以原始内容为事实来源。
4. 缺少某个表单字段不应自动写“无”，应视为未提供。

## 时间范围

- 优先使用用户给出的起止日期。
- 用户说“本周”但没有给日期时，以当前日期所在自然周（周一 00:00 至周日 23:59:59，Asia/Shanghai）为候选范围。
- 输入日期与当前周不一致时，采用输入日期所在的自然周，并在草稿开头写明周期。
- 只有星期、没有具体日期的记录，若能由上下文唯一确定则可补全；不能唯一确定时标记“日期待确认”，不要猜。
- 跨周粘贴时，保留与目标周期明确重叠的内容；无法判断归属的放在待确认项。

## 重复、冲突与缺失

### 重复

- 相同 `report_id`：去重。
- 同一天、同一模板、正文完全相同：去重。
- 不同日期描述同一工作的连续推进：不去重，进入事项归并。
- 不同批次、不同样品、不同对象或不同项目：即使措辞相似，也按独立记录保留。

### 冲突

同一事项出现互相矛盾的状态或数字时：

- 不自行裁决哪个版本正确。
- 保留两个版本和对应日期。
- 在草稿中使用不冲突的保守表述。
- 在“待确认”中说明冲突点。

### 缺失

- 无项目：根据明确的业务对象生成“项目候选”，但标注待确认；不要为了凑分类而硬塞进现有项目。
- 无结果：保留“开展”“处理”“跟进”等原动作，不自动补成“完成”。
- 无原因：未完成事项写“原因未说明”，不猜测原因。
- 无下周计划：写“未提供”，不生成承诺。
- 无未完成事项信息：写“未说明”；只有原始记录明确表示没有未完成事项时才写“无”。

## 提问门槛

只在以下情况集中提问，累计最多 3 个：

- 日期无法归属，且会改变本次周报范围。
- 同一事项存在两个项目归属，影响主体结构。
- 数量可能重复计入，导致结论错误。
- 关键完成状态无法判断，且会显著改变汇报内容。

其他问题先按中性措辞起草，并在文末集中列出。不要针对每条日志逐条追问。

## 多人日志

默认按提交人生成各自的周报，不把不同人的工作合并成一个人的成果。用户明确要求团队周报时，保留提交人归属，并分别说明个人完成情况和团队汇总；无法确认归属的事项不能计入个人成果。
