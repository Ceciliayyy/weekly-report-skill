# 术语规范化

目标是把口语整理成准确、清楚、适合管理工作汇报的表达，不是把普通工作包装得“更高级”。

准确优先于专业感。无法在不改变含义的情况下升级措辞时，保留原意并使用中性表达。

## 允许的改写

- 同义润色：不改变动作、对象、范围、完成度和责任主体。
- 结构压缩：删掉重复和口头语，合并同一事项的宾语与结果。
- 通用术语替换：把含糊口语换成没有额外含义的标准动作词，例如“看了一下”改为“检查”，“聊了”改为“沟通”。
- 明确缩写：原文已经出现或上下文明确时，可使用常用缩写，并在首次出现时写全称。

## 禁止的含义升级

| 原记录 | 可以写 | 不可以写 | 原因 |
|---|---|---|---|
| 参与需求讨论 | 参与需求讨论 | 负责需求分析 | 责任主体被放大 |
| 和研发讨论方案 | 开展方案沟通 | 完成方案确认 | 讨论不等于确认 |
| 写需求文档的一部分 | 完成需求文档部分内容编写 | 完成需求文档 / 完成 PRD | 局部被写成整体 |
| 改了几个模型参数 | 完成模型参数调整 | 模型效果提升 | 没有验证结果 |
| 看了一下测试结果 | 开展测试结果检查 | 完成测试验收 | 检查不等于验收 |
| 把数据上传到服务器 | 完成数据上传 | 完成系统上线 | 操作范围被放大 |
| 计划下周上线 | 下周计划上线 | 已完成上线 | 计划被写成完成 |
| 初步制图 | 完成初步制图 | 完成正式制图 | 阶段被拔高 |
| 发现两个问题，修复一个 | 发现 2 个问题，已修复 1 个 | 问题已全部解决 | 数量与状态失真 |
| 协助整理材料 | 协助整理材料 | 负责材料编制 | 角色被改写 |

## 状态词

只使用原始记录明确支持的状态：

```text
计划 / 启动 / 开展 / 初步完成 / 部分完成 / 完成 /
已提交 / 待评审 / 评审通过 / 已验证 / 已发布 / 已上线
```

不要用“持续推进”“稳步开展”“基本完成”等模糊说法掩盖未知状态。确实没有新进展时，可以不写；需要保留时，用“未见新增进展记录”并标为待确认。

## 动作与阶段

- “讨论、沟通、评审、确认、定稿”是不同阶段，不能互相替代。
- “开发、自测、提测、验收、发布、上线”是不同阶段，不能把自测写成验收，或把发布写成上线。
- “数据整理、数据处理、数据入库、数据发布”是不同阶段，按原文保留。
- “训练、推理、评估、调参、结果检查”是不同阶段，不能只写“优化模型”。
- “参与、协助、支持、负责、牵头”表达不同责任范围，不能升级。

## 不确定时怎么写

优先使用不增加信息的中性表达：

- 不清楚是否完成：“开展……”“处理……”“跟进……”。
- 不清楚是否验证：“完成……检查”“形成……初步结果”。
- 不清楚是否上线：“完成……发布准备”“开展……部署”。
- 不清楚是否最终定稿：“形成……初稿 / 提交……版本”。

如果术语选择会显著影响对成果的判断，把原句、建议措辞和不确定点放入“待确认事项”，正式稿使用保守表达。不要为了等待所有术语确认而中止整份周报。

## 管理者可读性

- 首次出现不常见的缩写时，补一次中文全称，例如“产品需求文档（PRD）”。
- 同一周报内统一术语：同一对象不要一会儿叫“系统”、一会儿叫“平台”，除非原始记录明确区分。
- 不堆砌技术名词；名词必须帮助读者理解对象、阶段或结果，否则删掉。
- 不使用自制词、空泛口号和夸张评价。
